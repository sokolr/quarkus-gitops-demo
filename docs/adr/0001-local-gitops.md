# ADR 0001: локальний GitOps для двох Quarkus-сервісів

**Статус:** прийнято. **Контекст:** навчальний приклад із локальним Kubernetes;
GitHub — єдиний віддалений компонент інфраструктури.

## Кластер і образи

Використовуємо Minikube з Docker driver, `containerd` та окремим профілем
`gitops-demo`. Це дає звичайні Kubernetes Deployment, Service та probes і
дозволяє `make down` видаляти весь навчальний кластер, не зачіпаючи профіль
`minikube`. Образи передаємо через `minikube image load`; локальний registry
не потрібний для одного вузла. Новий clone може зібрати відсутні образи з коду.

Наслідок: образи не зберігаються в Git і не доступні автоматично іншому вузлу.
Теги не перевикористовуємо для нового релізу; локальна повторна збірка того
самого тегу на іншій машині може дати інші байти. Для побітової тотожності
потрібен спільний registry і посилання на digest.

## Репозиторій і manifests

Код A, код B, Dockerfile, Kustomize та ArgoCD Applications тримаємо в одному
публічному репозиторії. Один commit може зв'язати зміну коду з бажаною версією
образу; публічний Git дозволяє ArgoCD читати manifests без credentials.

Kustomize base містить спільні Deployment, Service і ConfigMap, а local
overlays задають namespace та конкретні теги. Окремі overlays A і B дають
кожному сервісу власну ArgoCD Application. Root Application зберігається в
Git і створюється одноразово під час bootstrap; надалі ArgoCD автоматично
синхронізує дочірні Applications.

## Збій B і health A

A викликає B за Kubernetes Service DNS із ConfigMap. Connect і read timeout —
по 1000 мс, повторів немає. HTTP-помилку B, обрив з'єднання й timeout A
відображає як `502` із `SERVICE_B_UNAVAILABLE`; причину та correlation ID
записує в лог. Це зберігає визначений контракт для клієнта.

Readiness A залишається `UP`, коли B недоступний: A здатен прийняти запит і
повернути визначену відповідь `502`. Liveness перевіряє сам процес A і не
викликає його перезапуск через збій B. Readiness B означає готовність його
HTTP-сервера; B не має зовнішніх залежностей. Якщо залежності або контракт
готовності зміняться, ці перевірки потрібно переглянути.

## Просування версій

`make release SERVICE=…` тестує вибраний модуль, збирає образ із новим тегом
`release-<UTC-час>-<Git-SHA>`, завантажує його в Minikube та змінює тільки
`newTag` відповідного overlay. Людина переглядає diff і окремо робить commit
та push. ArgoCD читає Git, тому саме Git-коміт переводить Deployment на новий
тег; ручний `kubectl apply` до сервісів не входить у звичайний шлях.

Bootstrap налаштовує опитування Git кожні 30 секунд без jitter. Webhook не
потрібний для локального профілю:
GitHub не має сталої зовнішньої адреси локального ArgoCD. Для демонстрації
недоступності B змінюємо число реплік через Git; ручний `kubectl scale`
може бути скасований налаштованим `selfHeal`.
