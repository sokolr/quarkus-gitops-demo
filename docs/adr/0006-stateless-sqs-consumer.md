# ADR 0006: stateless SQS consumer у Service A

## Рішення

- Service A опитує стандартну SQS чергу через AWS SDK v2. SNS subscription
  використовує raw message delivery, тому consumer читає безпосередньо JSON
  доменної події, без SNS envelope.
- Поточна дія consumer — перевірка структури та значень події v1. Лише після
  успіху він викликає `DeleteMessage` із receipt handle цього отримання.
  Помилки перевірки і видалення залишають повідомлення для повтору.
- Черга має visibility timeout 30 секунд і redrive після трьох отримань.
  Consumer бере одне повідомлення за раз; його обробка обмежена 10 секундами,
  кожен виклик SQS — 5 секундами. При повторних помилках повідомлення має
  потрапити в DLQ.
- Consumer не зберігає стан і не має бізнес-ефектів, тому повторна доставка
  та зміна порядку повідомлень не змінюють бізнес-даних. Це відповідає
  поточному обсягу роботи; для майбутніх ефектів знадобиться окрема стійка
  ідемпотентність.

## Наступні кроки

Версія v2 події потребуватиме сумісної схеми валідації, перш ніж Service B
почне надсилати новий формат. Під час canary старі та нові Pod A конкурують
за одну чергу незалежно від HTTP-ваг; аналіз доставки має це врахувати.
Інтеграційні тести з реальним емулятором та демонстрація duplicate/DLQ
залишені на фінальний етап перевірки задачі.
