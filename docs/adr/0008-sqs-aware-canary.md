# ADR 0008: SQS сигнал у canary Service A

## Рішення

HTTP-аналіз залишається обов'язковим. Для A додаємо другий AnalysisTemplate,
який вимірює успіх опитування SQS та частку помилок обробки повідомлень із
метрик лише нового Pod hash. Лічильники створюються при старті Pod; Prometheus
збирає `/q/metrics` окремо від Istio stats. Порожнє вікно опитування дає 0%
успіху й блокує promotion. Порожнє вікно повідомлень дає 0% помилок, бо
обробляти було нічого; сигнал доступності черги надає poll metric.

Два Pod A (stable та canary) конкурують за одну стандартну SQS чергу. Їхня
частка повідомлень не пов'язана з HTTP-вагами Istio і не гарантується на рівні
SQS. Тому message metric оцінює тільки повідомлення, які потрапили до canary,
а poll metric дає постійний сигнал навіть за порожньої черги. Нульове
навантаження не доводить якість обробки payload; це обмеження прямо вказано
в README та має бути доповнене інтеграційними тестами на фінальному етапі.

Контрольований `DEMO_SQS_POLL_FAULT_PERCENT=100` змушує новий Pod провалити
всі опитування, залишаючи readiness і HTTP-запити справними. Аналіз має
автоматично відхилити такий canary; stable продовжує читати чергу. Повернення
значення `0` у Git відновлює здоровий Pod template. Продукційна конфігурація
завжди має значення `0`.
